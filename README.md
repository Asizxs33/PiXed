# PiXed

**PiXed** — образовательная игровая платформа в эстетике 16/32-bit RPG. Интерфейс построен на React и TypeScript, игровые режимы планируется развивать на Phaser.

## Локальный запуск

```bash
pnpm install
pnpm dev
```

Проверка production-сборки:

```bash
pnpm build
```

## Технологии

- React + TypeScript
- Vite
- Tailwind CSS
- Framer Motion
- Phaser 3
- локальные пиксельные шрифты

# Протокол совместной работы людей и AI-агентов

В проекте одновременно работают:

- **Asizxs33** — платформа, дизайн-система и интеграция интерфейса.
- **mansurkenma54** — игровые механики, Phaser и игровая логика.

Главное правило: **никто не работает напрямую в чужой ветке и никто не отправляет незавершённый код в `main`.**

## 1. Ветки

Ветка `main` содержит только проверенный рабочий код.

Для каждой задачи создаётся отдельная ветка:

```text
ui/<задача>          — интерфейс и визуальные компоненты
game/<задача>        — Phaser и игровые механики
feature/<задача>     — новая общая функция
fix/<задача>         — исправление ошибки
docs/<задача>        — документация
```

Примеры:

```text
ui/profile-screen
game/capture-the-flag
feature/auth-flow
fix/mobile-navigation
```

Перед началом каждой задачи:

```bash
git switch main
git pull --ff-only origin main
git switch -c game/capture-the-flag
```

Нельзя использовать одну ветку для нескольких независимых задач.

## 2. Разделение зон ответственности

| Зона | Основной исполнитель | Разрешённые директории |
|---|---|---|
| Общий UI и дизайн-система | Asizxs33 / его AI-агент | `src/components/`, `src/styles/`, `src/pages/` |
| Phaser и игровые сцены | mansurkenma54 / его AI-агент | `src/game/`, `src/scenes/`, `src/entities/` |
| Игровые данные и правила | mansurkenma54 / его AI-агент | `src/game-data/`, `src/game/` |
| Изображения и UI-ассеты | Asizxs33 / его AI-агент | `public/assets/` |
| Интеграционные файлы | Только по согласованию | `src/App.tsx`, `src/main.tsx`, `package.json`, `vite.config.ts` |

Если нужной директории ещё нет, агент может её создать.

Файлы из строки **«Только по согласованию»** нельзя менять двум агентам одновременно. Перед изменением нужно написать второму участнику, какой файл занят и для какой задачи.

## 3. Правила для AI-агентов

Каждому AI-агенту в начале задачи нужно передать этот текст:

```text
Работай только в отдельной Git-ветке. Сначала прочитай README.md и проверь git status.
Не изменяй файлы, принадлежащие зоне второго участника.
Не выполняй git push --force, git reset --hard и не удаляй чужие изменения.
Не коммить секреты, .env, токены, пароли и сгенерированные временные файлы.
Перед завершением запусти pnpm build.
Сделай небольшой понятный коммит и открой Pull Request в main.
Если нужен общий файл, остановись и сообщи об этом владельцам проекта.
```

AI-агент обязан сначала выполнить:

```bash
git status
git branch --show-current
git pull --ff-only origin main
```

Если рабочая директория содержит неизвестные изменения, агент **не должен их удалять или перезаписывать**.

## 4. Коммиты

Один коммит должен решать одну понятную задачу.

Формат сообщений:

```text
feat: add capture the flag scene
ui: improve player HUD
fix: prevent duplicate room connection
docs: update collaboration workflow
```

Перед коммитом:

```bash
pnpm build
git status
git diff --check
```

После проверки:

```bash
git add <только файлы текущей задачи>
git commit -m "feat: описание задачи"
git push -u origin <имя-ветки>
```

Не использовать `git add .`, если в рабочей директории есть изменения другого человека.

## 5. Pull Request

Все изменения попадают в `main` только через Pull Request.

В описании PR обязательно указать:

```markdown
## Что сделано
- ...

## Какие файлы изменены
- ...

## Как проверить
1. ...

## Проверки
- [ ] pnpm build
- [ ] Страница проверена в браузере
- [ ] Чужие файлы не затронуты
```

Перед слиянием второй участник должен просмотреть PR. Автор PR не сливает его, пока проверка не завершена.

## 6. Как избежать конфликтов

1. Не брать две задачи, которые меняют один файл.
2. Каждый день начинать с обновления `main`.
3. Делать небольшие PR, а не один огромный PR за несколько дней.
4. Общие типы хранить в `src/types/`, данные — в `src/data/`, UI — в `src/components/`.
5. Не размещать игровую логику внутри React-компонентов.
6. Не размещать React-интерфейс внутри Phaser-сцен.
7. Если конфликт уже появился, не выбирать автоматически `Accept all incoming/current`; сначала сравнить обе версии с автором второго изменения.

Обновление своей ветки перед PR:

```bash
git fetch origin
git rebase origin/main
pnpm build
```

После начала совместной работы запрещён `push --force` в `main`. Если после rebase нужно обновить личную ветку, допускается только:

```bash
git push --force-with-lease
```

и только после проверки, что ветку не использует второй участник.

## 7. Предлагаемый план первого спринта

### Asizxs33 / UI-агент

1. Разделить большой `App.tsx` на независимые компоненты.
2. Создать `src/components/layout/`, `src/components/game/` и `src/components/hud/`.
3. Перенести общие дизайн-токены в `src/styles/`.
4. Подготовить страницы «Игры», «Профиль» и «Рейтинг».

### mansurkenma54 / Game-агент

1. Создать `src/game/` и базовую конфигурацию Phaser.
2. Реализовать отдельную тестовую сцену без изменения дизайна главной страницы.
3. Добавить движение игрока и загрузку pixel-art ассетов.
4. Описать публичный API между React и Phaser в `src/game/types.ts`.

### Общая интеграция

После завершения двух независимых PR:

1. Asizxs33 объединяет проверенные изменения в `main`.
2. Создаётся отдельная ветка `feature/react-phaser-bridge`.
3. В этой ветке подключается Phaser-сцена к React-странице.
4. Оба участника проверяют сборку и браузер перед слиянием.

## 8. Запрещённые действия

- Прямой push в `main` без проверки.
- `git push --force` в общие ветки.
- `git reset --hard` для удаления неизвестных изменений.
- Изменение одной функции двумя агентами одновременно.
- Добавление секретов и `.env` в Git.
- Публикация или деплой без согласования владельца проекта.
- Массовое форматирование файлов, не относящихся к задаче.
